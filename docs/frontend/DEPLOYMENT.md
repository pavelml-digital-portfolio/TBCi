# Публикация на tbci.pavelml.ru

Цель: Masterhost `87.242.65.97`, SSH `vps-deploy`, порт `22`. Закрытый ключ — только GitHub repository Secret `VPS_DEPLOY_SSH_KEY`. Значение не хранится в репозитории и не запрашивается в чате.

## Подготовленный процесс

Workflow **Publish TBCi** запускается вручную в Actions с ветки `main`. Он сначала вызывает общую проверку фронтенда: установка из lock-файла, TypeScript, production-сборка и 12 браузерных сценариев. Проверенная статическая сборка передаётся в следующий job как artifact.

Выкладка загружает архив по SSH, сверяет SHA-256, распаковывает новый каталог релиза и атомарно переключает `current`. Старые релизы сохраняются. После переключения проверяются действительный HTTPS-сертификат, идентификатор релиза, лендинг и HTML-оболочка ЛК. При неудаче этих проверок workflow возвращает прежнюю ссылку `current`. Перезапуск Node на VPS не нужен.

Публичные действия с реальными средствами не реализованы. Авторизация по заданию отсутствует.

## Требования на VPS

- SSH должен быть доступен с GitHub-hosted runner. Подходящий секрет сам по себе не открывает firewall/сетевой доступ.
- `/var/www/tbci.pavelml.ru` должен существовать и быть доступным для записи пользователю `vps-deploy`; `current` должен отсутствовать либо быть символьной ссылкой.
- Веб-сервер должен обслуживать только `tbci.pavelml.ru` из `/var/www/tbci.pavelml.ru/current`, разрешать чтение файлов и обход каталогов.
- DNS A для `tbci.pavelml.ru` должен вести на этот VPS. Если есть AAAA, IPv6 также должен обслуживать сайт.
- Для домена нужен действительный HTTPS-сертификат и перенаправление HTTP → HTTPS, настроенные штатным способом сервера.

`scripts/deploy/tbci.nginx.conf` — готовый HTTP-виртуальный хост для Nginx с маршрутами Astro. Его нельзя устанавливать поверх чужого сайта. Перед подключением нужно проверить существующие виртуальные хосты и выбрать принятый на VPS способ настройки HTTPS. `nginx -t` обязателен перед reload. Автоматическая замена серверной конфигурации не выполняется.

Если SSH впервые подключается без заданного `VPS_SSH_KNOWN_HOSTS`, workflow получает открытые ключи через `ssh-keyscan` и использует `StrictHostKeyChecking=yes`. Для постоянного закрепления проверенного ключа задайте GitHub Variable `VPS_SSH_KNOWN_HOSTS` строками known_hosts, полученными по доверенному каналу.

## Диагностика и восстановление

Workflow **Inspect VPS** проверяет TCP-доступность, SSH-ключ, сервисы, каталоги и права на деплой. Он не изменяет сервер. Секреты не печатаются.

Каталоги релизов: `/var/www/tbci.pavelml.ru/releases/<commit>-<run>-<attempt>`. `previous` указывает на предшествующий релиз. Ручной откат: `scripts/deploy/publish-release.sh rollback <id-текущего-релиза>` на VPS от пользователя деплоя; скрипт откажет, если текущий релиз уже изменён. Не удаляйте каталоги, на которые указывают `current` или `previous`.

На момент подготовки кода публикация ещё не подтверждена. Из GitHub-hosted runners доступ к `87.242.65.97:22` нестабилен: один запуск получил баннер OpenSSH, остальные не завершили обмен ключами либо получили TCP timeout. Проверка чтения приватного ключа прошла, но SSH-аутентификация ещё не состоялась. Причина на стороне доступа/SSH сервера пока не установлена; необходимо проверить IP-фильтрацию, Fail2ban и журнал sshd на VPS. Локальная сборка и GitHub CI прошли. [Последняя сетевая диагностика](https://github.com/pavelml-digital-portfolio/TBCi/actions/runs/41093307403).

Скрипт переключения релизов отдельно проверен во временном каталоге: первая публикация, переключение, откат и отказ при неверном SHA-256. Это проверка скрипта, а не доказательство выкладки на VPS.
